# SD card editing audit — 1 November 2026

Scope: image-derived **Apply image edits to card** and **Recover card edits**,
including GUI/CLI preparation, the Linux client/helper boundary, device protection,
durable recovery data, cancellation, bounded writes and independent readback.
This is a source review plus regular-file fault testing, not an independent
security certification or a physical-hardware validation.

The audit started at commit `6b8059c` (1.1.0). Reproduced failures were fixed for
1.1.1. No attached card was opened, written, formatted or mounted/unmounted; no
system helper was installed. User images and backups were not modified.

## Findings and fixes

| Finding | Consequence in 1.1.0 | Fix and regression evidence |
|---|---|---|
| High: recovery compared only reader identity and journaled sectors | An older journal could undo sectors after unrelated filesystem changes elsewhere, or on another card in the same reader with matching affected sectors | Read the complete original-image range, normalize only known after sectors to before bytes in RAM, and require the original SHA-256. Tests reproduce both later edits and a different card in the same reader; neither permits a write |
| High: generated journal lacked a comparison against intended saved records | A damaged after record could be accepted as intended data because its later checksum was computed from the already damaged file | Flush/reopen and compare saved header, length and record checksum with generated bytes. Injected record corruption now prevents publication |
| High: reviewed journal identity was not carried into the helper | A changed valid journal could write different sectors/data from those prepared for review | Carry its verified SHA-256 through GUI/CLI and privileged request. A valid journal with different after bytes is rejected before card reads/writes |
| Defense gap: helper accepted a receipt-saved message without examining the actual receipt | The privileged boundary did not independently establish that the matching receipt existed on persistent independent storage | Require a published read-only receipt descriptor via SCM_RIGHTS; check owner, size, link, exact JSON, fsync, fingerprint, actual backing storage and current device use. Missing descriptors, cancel/disconnect, wrong content, deleted files, unsafe storage, new device use and flush failures reject the checkpoint |
| Medium: empty filesystem mappings returned an empty dependency set | Unresolved backing could be treated as independent storage | Reject absent/empty mappings. Both missing and empty `filesystems` results have regression tests |

Journal application also explicitly flushes existing journal files, rejects
unlinked files, and monitors the receipt after the checkpoint. The client syncs
the journal's directory before elevation. These checks cover journals prepared
or copied outside the desktop as well as its own generated journals.

## Retained protections reviewed

* Explicit destination selection and final review; GUI remains unprivileged.
* System/internal disks, protected filesystem backing, mounted/held devices,
  active raw-device users, zero capacity and missing disk sequence are rejected.
* Revalidation after authentication/exclusive open, then immediately before
  changed-sector writing; sequence, capacity and descriptor identity checks
  between bounded operations detect replacement during the operation.
* Normal application compares the entire original-image range before writing.
* Strict journal lengths, ordered/aligned/nonoverlapping offsets and bounds;
  immutable originals, preserved padding/unknown regions and larger-card tails.
* Only journaled 512-byte physical sectors are written. Writes are synced in
  bounded batches, the block cache is invalidated, and each written sector is
  independently read back. A source checksum alone cannot report success.
* Cancellation/failure never starts an automatic destructive retry. A failure
  after writing begins is explicitly incomplete/unverified; recovery stays manual.

## Verification

Run the offline suite with `.venv/bin/python -m pytest -q`. Added tests cover
the findings above, fragmented reads/writes, EOF/read errors, zero/partial writes,
failed journal/target flushes, insufficient journal storage, replacement at the
checkpoint, changed journals, mixed before/after recovery, and torn-sector refusal.
The GUI and CLI still exercise real preparation/application/recovery engines using
regular-file targets. Helper and client tests use real Unix sockets and SCM_RIGHTS,
with block open/stat/ioctl or process authentication replaced by controlled fakes.

The current counts and package/startup checks are recorded in [TESTING.md](TESTING.md).
No result here is a physical-card test.

## Remaining limits

1. A changed-sector journal is not a full backup. Keep a verified complete backup
   on independent persistent storage before relying on direct updates.
2. Power loss, removal or a partial write can leave a torn sector matching neither
   stored version. Journal recovery deliberately refuses such data. Use a complete
   backup for recovery; the app does not guess or silently repair it.
3. Recovery refuses unrelated later changes within the original-image range.
   Undo successive journals newest first. A shorter image's unwritten larger-card
   tail is preserved but is outside that journal's content comparison.
4. Linux exclusive claims, media-change reporting, cache invalidation, reader/card
   durability and actual CoCoNet loading still need the spare-card checklist in
   [TESTING.md](TESTING.md). Flush/readback cannot prove long-term flash retention.
5. Privileged or noncooperating external writers and faulty hardware cannot be
   controlled completely by advisory locks and fingerprints. Do not run another
   disk writer while this app owns the card.

Use the **1.1.1 app and helper together**. The app rejects the older helper's
card-edit protocol before authentication/device access. Install only after any
active card operation has finished; updating the helper itself does not open a card.
